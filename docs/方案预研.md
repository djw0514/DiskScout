# 磁盘占用排查软件方案预研

## 目标与约束

目标是同时覆盖 Windows 系统盘和普通数据盘，能定位大目录、大文件和异常占用，并且在面对权限目录、长路径、符号链接和海量小文件时保持稳定。第一版优先要求：安装简单、结果可信、默认安全、可在普通权限下工作，并允许用户按需提升权限。

## 候选方案

| 方案 | 扫描方式 | 优点 | 主要问题 | 结论 |
|---|---|---|---|---|
| A. NTFS MFT/USN 直读 | 调用 Win32 API 批量读取主文件表 | NTFS 全盘扫描速度最快，可取得文件 ID | 通常需要管理员权限；只适用于 NTFS；实现和验证成本高；网络盘、FAT/exFAT 仍需另一套逻辑 | 适合作为后续“极速模式”，不适合唯一引擎 |
| B. .NET/WPF 原生遍历 | 使用 `DirectoryInfo` 迭代枚举，后台线程扫描 | Windows 原生体验；无第三方依赖；兼容 NTFS/FAT/exFAT/网络目录；权限与错误可逐项处理；易于单文件发布 | 首次全盘扫描速度慢于 MFT；逻辑大小与实际分配空间可能不同 | 综合最优，选为第一版 |
| C. Windows Search/索引 | 查询系统索引数据库 | 已索引目录查询很快，CPU 和磁盘压力低 | 索引可能关闭或不完整；系统/开发目录常未索引；无法保证统计一致 | 只能做可选加速或历史搜索 |
| D. Electron/本地 Web 壳 | Node.js 枚举 + Web UI | 跨平台、界面开发快 | 分发体积和内存占用较高；Windows 权限、长路径和外壳集成更绕 | 当前目标是 Windows，不采用 |

## 选择

采用方案 B：`.NET 8 + WPF + 独立扫描核心`。这是当前约束下的综合最优解，而不是单纯追求跑分最快的解：它不依赖管理员权限和 NTFS，系统盘、普通盘、移动盘及指定目录可共用同一套可靠逻辑；发布后不需要用户另外安装 .NET。

架构上保留引擎边界。后续如遇到数百万文件的全盘扫描需求，可增加方案 A 的 NTFS 极速引擎，并在非 NTFS 或无管理员权限时自动回退到现有遍历引擎。

## 关键设计

1. 使用显式栈迭代目录，不使用递归调用，避免深层目录导致栈溢出。
2. 不跟随重解析点，避免目录联接、符号链接造成扫描循环或重复统计。
3. 单个目录无权限、路径过长或发生 I/O 错误时记录问题并继续扫描。
4. 文件扫描阶段直接累加当前目录大小，发现子目录时记录父对象；结束后按发现顺序逆向汇总，避免逐文件解析父路径及汇总前排序。
5. 大文件使用小顶堆只保留 Top N；堆满后先比较最小候选大小，仅为能进入榜单的文件创建结果对象并更新堆。
6. 扫描在后台线程执行，进度限频上报，界面可随时取消。
7. 第一版不直接删除文件；通过资源管理器定位后由用户确认处理，降低系统盘误删风险。

## 已知边界与演进方向

- 当前展示逻辑大小，不是 NTFS 实际分配大小；可增加 `GetCompressedFileSize` 统计物理分配量。
- 硬链接可能重复计入逻辑大小；可通过卷序列号 + File ID 去重，但会增加每文件一次系统调用。
- 系统还原点、卷影副本和部分回收站内容可能无法逐文件枚举；可增加 VSS/系统存储专项诊断。
- 可增加快照数据库，对比“本周比上周增长最多的目录”。
- 可增加 MFT 极速模式、树图可视化和清理前后的空间复核，但删除仍应进入回收站并进行二次确认。

## 验收标准

- 递归目录容量、文件数和分类统计正确。
- Top N 大文件正确，扫描过程中可取消。
- 遇到无权限目录不会导致全盘扫描失败。
- 重解析点不被跟随。
- Debug/Release 均可编译，核心冒烟测试通过，可生成 win-x64 单文件发布物。
